## 2. Reconstruction and disk rebuild

| lost shards | type | rebuilt MB/s (output) | survivor MB/s read |
|---|---|---|---|
| (0,) | data | 5,652 | 22,609 |
| (0, 1) | data+data | 5,708 | 11,417 |
| (4,) | parity | 5,615 | 22,458 |
| (1, 5) | data+parity | 5,319 | 10,639 |

**Rebuild of one dead 4 TB disk (4+2, 6 disks) — extrapolated.** The replacement disk must receive 4 TB, and each rebuilt shard needs k=4 survivor reads (spread over 5 disks, 3.2 TB each). CPU decode at 5,652 MB/s of output would take **0.2 h**; the new disk's sequential write at ~180 MB/s takes **6.2 h**. Rebuild is therefore **disk-bound at ≈6.2 h**, with decode using 3% of one core. With the default 150 MB/s rebuild throttle (to keep foreground reads responsive) the figure is ≈7.4 h.

## 7. Content-defined chunking: media vs non-media (honest numbers)

| corpus | files | logical MB | unique MB after CDC | CDC dedup × | avg chunk KiB | zstd per-file × | zstd batch+dict × |
|---|---|---|---|---|---|---|---|
| non-media: all stdlib source + revisions | 1009 | 24.02 | 23.10 | 1.04 | 20.57 | 4.70 | 7.42 |
| non-media: large docs only (≥100 KB) + revisions | 73 | 12.86 | 11.20 | 1.15 | 61.28 | 5.81 | 7.86 |
| media: JPEG (sensor noise) + edited copies | 80 | 32.41 | 32.41 | 1.00 | 67.91 | 1.00 | 1.01 |

Reading the table honestly: **CDC's gain on media is nil** (edited photos are re-encoded, so no byte ranges survive) and zstd barely touches JPEG — media goes to the erasure-coded tier uncompressed, as designed. On typical documents most files are smaller than the 16 KiB minimum chunk, so an edit rewrites the file's only chunk and CDC adds little; CDC pays off on **large** documents with revisions. For the non-media tier as a whole, the bigger win is **batch compression with a trained dictionary** versus compressing each file alone.

Chunking throughput: **397 MB/s** native C (native), 4.6 MB/s pure-Python reference (818 chunks over 64 MiB random data).

Bloom filter (1 M chunks, 1.1 MiB, k=7): measured false-positive rate **0.992%** (target 1%), 0.9 µs per probe — i.e. 99.0% of new-chunk lookups skip the SQLite index entirely.

## 8. Thumbnail cache

| budget MB | LRU hit rate | LRU SSD loads | LRU+prefetch hit rate | LRU+prefetch SSD loads |
|---|---|---|---|---|
| 16 | 0.58 | 41784 | 0.99 | 42301 |
| 32 | 0.62 | 38099 | 0.99 | 38631 |
| 64 | 0.66 | 34520 | 0.99 | 34988 |
| 128 | 0.71 | 28980 | 0.99 | 29847 |
| 256 | 0.81 | 19065 | 0.99 | 19556 |

Prefetch converts request-path misses into background loads: the hit rate rises because the next half-page is already warm, while total SSD loads stay similar (the column on the right).

Trace: 100,680 thumbnail requests over 20,000 items. The default budget (256 MB) holds the working set of a heavy browsing session; the server-side cache sits behind the browser's own HTTP cache (thumbnails are served `immutable`), so it mostly absorbs cross-device and post-restart traffic.
